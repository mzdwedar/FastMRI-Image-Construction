# Spec: observability

Module of [SPEC.md](SPEC.md). Depends on: `gateway`, `inference-server`.

## Objective

An operator can answer "is it healthy, is it meeting its SLOs, and if not, why" from Grafana alone, and gets
paged (Alertmanager) on user-facing symptoms before users complain. Metrics, logs, and traces share a
`request_id` / `trace_id`, so one request can be followed from gateway to Triton.

## Current state (baseline)

Prometheus scrapes FastAPI and Triton; Grafana provisions two dashboards generated by `build_dashboards.py`;
an in-process `psutil` thread exports host CPU/memory. No alerting, no logs pipeline, no tracing, no SLOs.

## Stack (Compose services, all images pinned)

| Service | Role |
|---|---|
| prometheus | scrape + rule evaluation, 15 d retention, `--web.enable-lifecycle` |
| alertmanager | routing; default receiver is a webhook to a local `alert-sink` (logs alerts, used by e2e); Slack receiver enabled when `SLACK_WEBHOOK_URL` is set |
| grafana | provisioned datasources (Prometheus, Loki, Tempo with trace↔log↔metric links) and dashboards; anonymous viewer, admin password from secret |
| loki | log storage (single binary, filesystem, 7 d retention) |
| tempo | trace storage (local backend, 3 d retention), metrics-generator off |
| alloy | Docker log discovery → Loki; OTLP gRPC/HTTP receiver → Tempo |
| node-exporter | host metrics |
| cadvisor | per-container CPU, memory, throttling (replaces the psutil thread, which is deleted) |

## Requirements

### Metrics (gateway; Triton's `nv_*` metrics as-is)

| Metric | Type | Labels |
|---|---|---|
| `gateway_requests_total` | counter | `route`, `method`, `status_class` |
| `gateway_request_duration_seconds` | histogram | `route` (buckets 5 ms … 60 s) |
| `gateway_inflight_requests` | gauge | — |
| `gateway_rejected_total` | counter | `reason` (`overloaded`, `too_large`, `unauthorized`, `invalid`) |
| `gateway_upload_bytes` | histogram | — |
| `gateway_slices_total` | counter | `route` |
| `gateway_stage_duration_seconds` | histogram | `stage` (`preprocess`, `triton`, `encode`) |
| `gateway_triton_errors_total` | counter | `code` (gRPC status) |
| `gateway_model_ready` | gauge | — (from the readiness loop) |
| `gateway_model_info` | gauge = 1 | `version`, `preprocess_version` |

Labels never include request ids, filenames, or API keys (bounded cardinality).

### Logs

`structlog` JSON to stdout, one line per request at INFO plus errors: `ts, level, event, request_id, trace_id,
span_id, route, method, status, duration_ms, slices, model_version, client` (key id hash, not the key). Uvicorn
access logs disabled (replaced by ours). Alloy labels: `service`, `level` only.

### Traces

OpenTelemetry SDK in the gateway (FastAPI auto-instrumentation + the manual spans named in SPEC-gateway), W3C
trace context forwarded to Triton in gRPC metadata; Triton `--trace-config mode=opentelemetry` exports its
request/compute spans to Alloy. Sampling: parent-based, ratio `OTEL_TRACES_SAMPLER_ARG` (1.0 in dev, 0.1 default);
errors and requests slower than 2 s are always kept (Alloy tail sampling).

**O9 finding (2026-11-12): Triton propagates the trace context, so the plan stands (no fallback).** Spike on
`tritonserver:24.08-py3` (arm64), `unet_model` on ONNX Runtime CPU, an OTel Collector with the debug exporter:

- Flags: `--trace-config mode=opentelemetry --trace-config opentelemetry,url=<alloy>:4318/v1/traces
  --trace-config rate=1 --trace-config level=TIMESTAMPS --trace-config count=-1`. The exporter is OTLP/HTTP, so Alloy
  needs the HTTP receiver on 4318 (the gateway can use gRPC 4317).
- A gRPC `infer` carrying `traceparent` metadata produced three Triton spans under the caller's trace id:
  `InferRequest` (its parent is the caller's span id) > `unet_model` (events `REQUEST_START`, `QUEUE_START`,
  `REQUEST_END`) > `compute` (`COMPUTE_START`, `COMPUTE_INPUT_END`, `COMPUTE_OUTPUT_START`, `COMPUTE_END`). Queue wait
  and compute time are therefore visible per request. `service.name` is `triton-inference-server`.
- gRPC metadata keys must be lowercase (`traceparent`); the Python client rejects `Traceparent` before sending.
  The gateway passes it through `infer(..., headers={"traceparent": ...})`.
- A request without `traceparent` gets a fresh root trace (never an error).
- **Triton ignores the sampled flag.** A `traceparent` ending `-00` was still traced and exported. With `rate=1`
  every request produces Triton spans, so the gateway's head sampling (ratio 0.1) does not reduce Triton's span volume.
  O8 must therefore run the keep/drop decision in Alloy's tail sampling for the whole trace (errors, > 2 s, plus a
  probabilistic share), and must not assume a trace is complete or absent just because the gateway did not sample it.
  Not tested: a Triton `rate` above 1 combined with a propagated context, and Alloy's tail-sampling behaviour.

### SLOs (initial targets; calibrated after gateway baseline; changes require approval)

| SLO | SLI | Target | Window |
|---|---|---|---|
| Availability | non-5xx responses / all responses on `/v1/*` (4xx count as good) | 99.5% | 30 d |
| Interactive latency | `/v1/infer` single-slice requests < 250 ms | 99% | 30 d |
| Volume latency | `/v1/reconstructions` < 5 s | 95% | 30 d |

Recording rules compute SLI ratios over 5m/30m/1h/6h; alerts use multi-window burn rates (14.4× over 1h & 5m →
page; 6× over 6h & 30m → ticket).

### Alerts (`monitoring/prometheus/rules/*.yml`)

| Alert | Condition | For | Severity |
|---|---|---|---|
| `GatewayDown` | `up{job="gateway"} == 0` | 1m | page |
| `TritonDown` | `up{job="triton"} == 0` | 1m | page |
| `ModelNotReady` | `gateway_model_ready == 0` | 2m | page |
| `AvailabilitySLOBurnFast/Slow` | burn-rate rules above | — | page / ticket |
| `LatencySLOBurnFast/Slow` | burn-rate rules above | — | page / ticket |
| `TritonQueueSaturation` | avg queue time per request > 50% of compute time over 10 m | 10m | ticket |
| `GatewayRejectingLoad` | `rate(gateway_rejected_total{reason="overloaded"}[5m]) > 0` | 10m | ticket |
| `ContainerMemoryHigh` | working set > 90% of limit (cAdvisor) | 5m | ticket |
| `ContainerCPUThrottled` | throttled periods ratio > 25% | 15m | ticket |
| `PrometheusTargetMissing` / `AlertmanagerNotifyFailing` | meta-monitoring | 5m | ticket |

Every alert has `summary`, `description`, and a `runbook_url` pointing to `docs/runbooks/<alert>.md` (written in this
module, one page each: symptoms, dashboards, likely causes, remediation commands).

### Dashboards (generated by `monitoring/grafana/build_dashboards.py`, committed JSON)

1. **Service overview**: SLO status and error budget remaining, request rate, error rate, p50/p95/p99 by route,
   in-flight, rejections, served model version.
2. **Triton**: inference rate, queue vs compute time, batch size distribution (from `nv_inference_exec_count` vs
   `nv_inference_count`), per-version counts, pending requests.
3. **Infrastructure**: container CPU/mem/throttling, host metrics.
4. **Model**: populated by model-monitoring.
Grafana links: request-rate panel → Loki query by route; log line `trace_id` → Tempo; Tempo → logs by trace.

## Commands

```

```

## Testing strategy

- `promtool test rules monitoring/prometheus/tests/*.yml`: every alert has a firing and a non-firing test case;
  burn-rate math checked with synthetic series.
- Unit: metrics registered with the expected names/labels; a request produces exactly one access log line with
  matching `request_id` and `trace_id`; no API key or filename in log output.
- E2E (Compose): send 10 requests → Prometheus `gateway_requests_total` ≥ 10; Loki returns the log line for a
  known `request_id`; Tempo returns a trace for it containing gateway spans and a Triton span; stop Triton →
  `TritonDown` reaches `alert-sink` within 2 min.
- Dashboards: generator output equals committed JSON; every panel query is valid (Prometheus API `query` returns no
  error) in e2e.

## Boundaries

- Always: add a runbook with every new alert; keep label cardinality bounded.
- Ask first: changing SLO targets; adding a paid/external receiver; retention increases.
- Never: alert on causes (CPU %) at page severity; log payloads or PHI-like metadata from `.h5` attrs.

## Success criteria

- [ ] `make check-configs` passes, including alert rule unit tests.
- [ ] System success criteria 3 and 4 in SPEC.md pass in the e2e suite.
- [ ] Four dashboards load without errors with live data; links between metrics, logs, and traces work.
- [ ] Each alert has a runbook; psutil-based `HardwareMonitor` removed.
